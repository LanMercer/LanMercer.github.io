大模型算法项目成果与AI辅助制作方案

作者： LanMercer
工程顺序： Day1～Day20，四周主线全部完成
实践项目： 机器人行业垂直领域RAG问答系统
硬件环境： NVIDIA RTX 3060 Laptop，6GB显存
AI协作方式： 对话助手制定教程与解释原理，代码助手协助实现与排错，本人学习、运行、修改并验收

一、项目背景与目标

这次实践按照 Day1～Day20 推进，从大模型基础学习出发，逐步把本地部署、提示词工程、接口服务、文档检索、参数高效微调、量化评测和在线交付整合成一个可以使用、可以复核、有完整文档的工程项目。

RAG（检索增强生成）是先从资料里找到相关内容，再让模型依据这些内容回答。我的目标是围绕机器人领域PDF建立知识库，让回答能够追溯到资料，同时在资料没有答案时明确说明，而不是编造结论。

项目选用Qwen2.5-3B-Instruct作为生成模型。QLoRA是将量化后的模型底座与少量可训练参数结合的微调方法，使有限显存也能进行训练；LoRA adapter是保存这些增量参数的适配器。项目同时保留原模型和微调模型，便于观察两条链路的差异。

数学背景也贯穿了学习过程：用概率分布理解softmax，用加权平均理解注意力，用余弦相似度理解检索，用低秩近似理解LoRA。类比帮助入门，最终结论仍以公式、代码和实测结果为依据。

二、四周工作过程：从基础学习到在线交付

整个项目按照 Day1～Day20 推进，每周包含一份阶段小结，并按天记录当天完成的工作、形成的成果和对应意义。所有顺序均使用 Day 编号，不记录具体日历日期。

第一周：理解 Transformer，建立大模型学习基础

本周小结

第一周的目标是完成开发环境搭建，并从数学和代码两个角度理解 Transformer 的核心结构。这一周没有急于调用现成的大模型应用，而是从注意力机制、位置编码、残差连接、LayerNorm 和前馈网络开始，逐步建立完整的结构认知。最终完成了手写注意力验证、位置编码实验、简单序列模型训练和 Transformer 结构图定稿。

第一周最大的收获，是把过去停留在名词层面的知识转化成了能够计算、能够画图、能够运行代码验证的理解。

Day1：搭建大模型开发环境

工作内容： 使用 Miniconda 建立独立 Python 环境，安装 GPU 版 PyTorch 及 Transformers、Datasets、Accelerate 等依赖；检查 CUDA、显卡驱动和 PyTorch 的兼容情况，确认代码能够调用 GPU，并建立模型权重、代码、实验结果和学习文档的目录规范。

工作成果与意义： Day1 解决了后续全部实验的基础设施问题。通过实际处理依赖版本、CUDA 匹配和模型文件管理，建立了环境问题逐层排查的工程意识。

Day2：建立 Transformer 整体认知

工作内容： 学习 Encoder、Decoder、自注意力、多头注意力和位置编码的整体关系，梳理输入文本经过 Embedding、注意力层、前馈网络到输出的完整路径，并使用概率分布和加权平均的视角理解 softmax 与注意力，绘制第一版 Transformer 整体结构图。

工作成果与意义： Day2 完成了从“知道 Transformer”到“能够说明数据怎样在模型中流动”的转变，为后续拆解注意力计算和手写代码建立了整体框架。

Day3：理解并手算注意力机制

工作内容： 学习 Query、Key、Value 三类向量的作用，手算 3×3 注意力权重矩阵，验证 softmax 后每一行权重之和为 1；使用方差可加性解释注意力分数为什么需要除以 √d，并修改词向量中的共享语义维度，观察“猫”和“狗”之间的注意力变化。

工作成果与意义： 加入共同的“动物”语义维度后，相关词之间的注意力权重由约 0.212 上升到 0.468。这说明词向量负责表达语义，注意力机制根据语义关系动态分配权重。Day3 把注意力从抽象公式转化成了可以手算和解释的概率矩阵。

Day4：手写多头注意力与位置编码实验

工作内容： 手写多头注意力计算流程并与 PyTorch 官方实现数值对比；完成有无位置编码的对照实验；使用 torch.nn.Transformer 训练序列倒序任务，同时处理张量形状、标签掩码和词表映射。

工作成果与意义： 手写多头注意力与官方实现的最大误差约为 5e-07。序列倒序实验的 loss 由 1.856 下降到接近 0，测试结果达到 10/10。Day4 第一次完成了“理解原理—自己实现—与官方对拍—训练模型”的完整验证闭环。

Day5：补齐 Transformer 结构并理解 LoRA

工作内容： 学习残差连接、LayerNorm 和前馈网络，完成包含注意力、残差、归一化与 FFN 的结构图；使用 NumPy 模拟低秩矩阵更新，通过 SVD 理解 LoRA 为什么可以用较少参数表达模型改动，并估算不同模型和量化方式的参数量与显存需求。

工作成果与意义： 参数计算显示，低秩更新相较全量参数可以节省约 99.55%。Day5 据此确定后续采用 Qwen2.5-3B-Instruct 和 4bit 量化，使项目能够在 6GB 显存设备上运行。

第二周：完成本地模型部署、提示词工程与 RAG 全链路

本周小结

第二周的目标是让模型真正“用起来”。这一周先完成 Qwen 本地部署，再通过提示词工程控制模型输出，随后把模型封装成 OpenAI 兼容接口，最后接入 PDF 加载、文本切块、Embedding 和向量数据库，形成第一版 RAG 文档问答系统。

第二周结束时，系统已经能够读取机器人论文、检索相关段落并生成带出处的回答。

Day6：本地部署 Qwen 模型

工作内容： 下载 Qwen2.5-3B-Instruct，使用 NF4 方式进行 4bit 量化加载，配置 device_map="auto"，对 temperature 和 top_p 进行多组采样对照，并建立模型权重不进入 Git 仓库的管理规则。

工作成果与意义： 模型加载后的显存占用约为 1.92GB，在 6GB 显存设备上成功完成本地推理。Day6 证明有限硬件也能完成 3B 模型部署，并建立了显存预算、模型量化与推理参数之间的联系。

Day7：提示词工程入门

工作内容： 学习角色、任务、输入、输出格式和约束条件五个组成部分，对比零样本、few-shot 和思维链提示，制作第一版提示词模板库，并对数学题进行思维链 A/B 实验。

工作成果与意义： 第一轮实验中，思维链提示将数学题正确率由 60% 提高到 84%。虽然样本量较小，但实验展示了提示词可以改变模型推理过程和输出分布。

Day8：提示词模板迭代与 RAG 标准模板

工作内容： 将模板库扩展到 20 个模板、5 类任务；对 JSON 结构化抽取模板进行多轮修改，增加字段约束、同构示例和输出格式要求；完成“只依据资料回答、标注资料编号、资料不存在时明确拒答”的 RAG 标准模板，并扩大思维链实验样本量。

工作成果与意义： 结构化抽取模板经过三轮修改后实现目标字段全部正确。扩大样本后的思维链实验由 20% 提高到 50%。这一阶段也形成了“推理任务交给模型，精确计算交给代码”的工程原则。

Day9：将本地模型接口化

工作内容： 使用 FastAPI 封装本地模型，实现 OpenAI 兼容的 /v1/chat/completions 接口，补齐请求参数和返回结构，并分别使用 curl、Python requests 和 LangChain 调用接口。

工作成果与意义： Day9 把只能在单个脚本中运行的模型变成了可以由不同应用统一调用的服务，为后续 RAG、Web UI 和双模型切换打下接口基础。

Day10：跑通 RAG 文档问答全链路

工作内容： 使用 PyPDF 读取机器人领域论文，将 9 页论文切分成约 105 个文本片段；使用 bge-small-zh-v1.5 生成向量，以 Chroma 保存向量与原文，通过余弦相似度执行 Top-K 检索，再将召回片段与提示词组合后交给 Qwen 生成回答；同时手写简化版向量检索与 LangChain 实现对照。

工作成果与意义： 早期 Demo 对 3 个论文问题均给出正确答案，并能够返回资料编号；面对资料中不存在的问题时也产生了正确拒答样例。Day10 完成了“上传文档—建立索引—检索资料—生成答案—返回出处”的核心闭环。

第三周：完成 QLoRA 微调、项目定型和量化评测

本周小结

第三周的目标是把前两周的独立实验整合成正式项目。这一周完成了 SFT 数据准备、QLoRA 训练、微调模型接口、20 题固定评测集、自动评测脚本和双模型问答入口。

第三周结束时，机器人行业 RAG 系统已经具备完整架构、可运行入口、量化基线和项目文档，但首版评测也暴露出检索召回不足和生成层幻觉问题。

Day11：准备 SFT 数据与微调环境

工作内容： 学习 SFT、QLoRA 和 PEFT 之间的关系，编写数据生成脚本，构建 300 条机器人行业三字段 SFT 数据，覆盖公告抽取、研报问答、要点总结、数据计算、合规判断和概念解释 6 类任务，并检查字段、空值、重复项、类别分布和 GPU 环境。

工作成果与意义： 数据集共 300 条，字段齐全、空值为 0、重复为 0。Day11 完成了模型训练前最重要的数据准备工作，也建立了“微调效果首先取决于数据设计”的认识。

Day12：完成 QLoRA 训练与前后对比

工作内容： 使用 4bit 量化底座加载 Qwen2.5-3B-Instruct，配置 LoRA 的秩、缩放系数和目标线性层；使用答案区间标签训练，记录训练 loss、验证 loss 和显存占用，保存 LoRA adapter，并用同一组问题对比原模型与微调模型。

工作成果与意义： 训练参数为 14,966,784 个，约占 3.10B 总参数的 0.4827%；adapter 约 20～30MB。初步 5 题对比中有 4 题表现出更明显的行业表达和任务格式变化，另 1 题错误被如实保留。Day12 证明微调能够改变表达方式，但“格式学会了”不等于“事实一定正确”。

Day13：完成项目定型与四层架构

工作内容： 将项目划分为检索层、答案组织层、风格/能力层和生成层，明确 RAG 负责事实、微调负责风格与任务习惯；建立 20 题固定评测集，编写微调模型接口，并完成项目架构图和接口冒烟测试。

工作成果与意义： 四层架构使问题能够按层定位：召回错误检查检索层，格式错误检查提示词，风格问题检查 adapter，逻辑错误检查生成层。Day13 把此前学习内容组织成了能够解释、演示和继续优化的工程系统。

Day14：建立首版量化评测基线

工作内容： 编写自动评测脚本，将 20 题分为 10 道资料内问题和 10 道资料外或反事实问题，分别评估检索命中率、资料内生成正确率、防幻觉正确率和防幻觉 F1，并逐题人工复核自动判分结果。

工作成果与意义： 首版结果为检索命中率 20%、资料内生成正确率 20%、防幻觉正确率 60%、总正确率 40%、防幻觉 F1 0.667。Day14 最大的价值不是得到高分，而是建立后续所有优化共用的评测基线，并暴露检索召回是主要瓶颈。

Day15：完成 MVP 整合与双模型入口

工作内容： 使用配置文件管理原模型和微调模型，使用统一问答脚本整合检索、提示词组织和生成流程，支持切换两条模型链路；完成双链路冒烟测试，并整理 README、效果评估报告、面试四问和测试记录。

工作成果与意义： Day15 将分散组件整合成统一入口。至此，项目具备“能运行、能切换、能评测、有文档”的 MVP 形态，也为第四周系统整改提供了明确起点。

第四周：可归因优化、真实数据建设与公网交付

本周小结

第四周的目标，是把第三周的本地 MVP 推进为可以展示、可以复核、可以公开访问的工程成品。这一周围绕优化、交付、数据和分析四条主线展开，最终完成 17 轮对比实验、12 行逐步骤贡献分析和 8 项失败尝试记录。

同口径下，检索命中率由 20% 提高到 40%，资料内生成正确率由 20% 提高到 40%，防幻觉 F1 由 0.667 提高到 0.824，总正确率由 40% 提高到 55%。第四周最重要的成果不只是指标提高，而是形成“固定评测—单变量实验—逐题排查—记录失败—明确边界—交付上线”的完整工程方法。

Day16：校准评测尺子，建立可比较的新基线

工作内容： 重构评测脚本，加入严格段落命中与上下文关键词命中的双轨判据、重复运行、多数投票、一致率、实验编号、自动记账以及逐题结果保存。完成尺子校准后，只改变 Top-K 一个变量，将召回片段数由 4 增加到 8。

实测结果： 检索命中率由 20% 提高到 40%，资料内生成正确率由 20% 提高到 40%，防幻觉正确率由 60% 提高到 70%，防幻觉 F1 提高到 0.824，总正确率由 40% 提高到 55%。同时保留了一条反例：增加 Top-K 后，个别问题因加入更多干扰片段而回答得更差。

工作意义： Day16 解决了“用什么尺子衡量优化”的问题。评测口径固定后，后续实验才能判断差异来自真实改善、随机波动还是评分变化。

Day17：复跑基线并验证检索假设

工作内容： 将关键实验统一为每题运行 3 次，以多数投票形成最终判断，同时记录三次结果的一致性；测试 bge instruction 前缀、Top-K 以及两者组合。

instruction 前缀单独使用时，严格检索命中率由 20% 下降到 0%。逐题检查发现，它并非让全部语义失效，而是改变了相似片段排名，使正确片段掉出 Top-K 窗口。前缀和 Top-K 同时变化时部分指标恢复，但因为两个变量一起变化，不能把结果归因给某一个因素。最终关闭前缀，保留 Top-K=8。

工作意义： Day17 说明官方推荐参数也必须在自己的模型、语料和题集上验证，并形成“每轮尽量只改变一个变量”的实验纪律。

Day18：确认检索瓶颈，建设论文真实数据并完成 Web UI

工作内容一：评测标注自检。 从目标片段是否存在、期望关键词是否位于标注片段、关键词是否实际只在其他片段三个方面检查资料内问题。10 道题中 9 道自动确认自洽，剩余 1 道经人工核对正确，最终为 0 个缺失片段、0 个错位标注。

工作内容二：拆分检索通道。 分别测试向量检索、BM25 和 RRF 融合。普通中文问题下，三种方式的严格命中分别为 4/10、4/10 和 3/10，三者并集覆盖 7/10；RRF 直接融合反而少命中一题，因为中文问题对英文论文的关键词信号太弱。将问题人工改写为理想英文查询后，三种检索均达到 10/10。该结果只作为诊断上界，不作为正式成绩。

工作内容三：建设论文真实数据。 从 GMR 论文中整理 90 条真实问答，覆盖术语、方法、实验设置、结论和局限；每条数据保存来源片段，完成 90/90 逐字回查，并确认不存在评测泄漏。

工作内容四：完成 Web UI。 补齐上传 PDF、重新建库、内置示例语料、带出处问答、召回可视化、Top-K 调整、双模型切换和服务身份检查。指标从实验结果动态读取，不在页面中硬编码。

工作意义： Day18 形成了完整诊断证据链：先排除标注问题，再拆分检索通道，最后用理想查询确认知识库上限，由此判断主要瓶颈是中文问题与英文论文片段之间的语言错位。项目也从命令行脚本推进到普通用户能够操作的 Web 产品。

Day19：查询改写、模板消融、引文白名单和真实行业数据

工作内容一：自动查询改写。 将 Day18 的人工上限变成自动方案。三档改写的总正确率分别为 45%、50% 和 55%，没有超过 Top-K=8 基线。部分方案提高了检索召回，却让资料外问题更容易检索到“看似相关”的内容，防幻觉表现反而下降。

工作内容二：提示词逐句消融。 新版模板三档均出现不同程度退化。问题集中在“资料里有依据就照实回答”这句提示：资料外问题同样会召回相似片段，小模型容易把“检索到了内容”误判成“找到了依据”。这类误读型幻觉无法只靠增加提示词约束解决。

工作内容三：引文合法性处理。 比较发现非法编号后重答与白名单剪除。重答会使部分正常问题变成拒答，防幻觉 F1 由 0.824 下降到 0.737；白名单剪除不改变任何正确性和拒答判断，并将数字型非法引用由 5 处降为 0，因此成为最终交付层兜底。

工作内容四：真实行业数据。 新增 111 条机器人行业真实问答，覆盖 26 个机构，每条保存来源 URL 和原文摘录，并检查重复、泄漏和类别分布。面对同一家公司在年报与监管问询中的不同口径，两种材料都被保留。它们与 90 条论文问答共同组成 201 条可追溯真实数据。

工作内容五：真实数据微调对照。 使用 201 条真实数据重新训练 LoRA，训练流程和检索结果均正常，但防幻觉 F1 由 0.824 下降到 0.333。由于这轮同时改变了数据来源与样本数量，因此没有草率得出“真实数据无用”的结论，而是将数量变量留到 Day20 单独验证。

工作意义： Day19 明确了局部指标上涨不等于端到端效果提升，也进一步划清了检索层、生成层和交付层的责任边界。

Day20：拆分变量、完成双模型对照并上线交付

工作内容一：拆分数据变量。 构建“201 条真实数据+99 条合成数据”的 300 条混合数据集，使样本数量与旧数据对齐。数量对齐后防幻觉 F1 仍只有 0.429，只比 201 条版本恢复 1 道题，说明退化主因不是少了 99 条样本，而是训练数据分布与固定评测集不匹配。

工作内容二：原模型与微调模型公平对照。 在相同知识库、Top-K、提示词、生成参数和 20 题评测集下，只改变是否加载 LoRA adapter。原模型防幻觉 F1 为 0.947、总正确率 80%；当前微调模型 F1 为 0.824、总正确率 55%。两轮检索结果逐位相同，差异来自生成层。

这是一个逆预期结果，只能说明“这版微调在这组防幻觉评测上表现更差”，不能推广为“微调没有用”。微调在专业术语、回答风格和格式遵循方面仍有作用。另一方面，原模型在相同检索结果下取得更好事实问答效果，也证明项目知识主要来自检索层，微调不能替代知识库。

工作内容三：完成优化报告与交付。 整理 17 轮对比实验、12 行逐步骤贡献、8 项失败尝试、优化前后对比图、定稿数字表、README、Web UI 发布包、内置示例语料、一键启动和环境自检工具，并完成公网部署。

最终上线成品：**https://modelscope.cn/studios/LanMercer/rag233**。

在线 Demo 无需上传文件即可使用内置 GMR 论文语料，也支持上传自己的 PDF 重新建库。在线版检索层使用项目真实实现；由于免费 CPU 环境无法运行本地 3B 模型，在线生成层使用 DeepSeek API。本地实验和本文评测数字使用 Qwen2.5-3B-Instruct 及 LoRA adapter，两者生成指标不能混合比较。

工作意义： Day20 完成了从学习实验到工程成品的最后一步：拆开混杂变量，完成公平双模型对照，如实保留微调负收益的逆预期结果，并把本地 RAG 系统包装为可以公开访问的在线产品。

三、四周工作总结

Day1～Day5 完成大模型原理与数学基础；Day6～Day10 完成本地部署、提示词工程、接口化和 RAG 全链路；Day11～Day15 完成 QLoRA 微调、项目定型、量化评测和 MVP 整合；Day16～Day20 完成可归因优化、真实数据建设、Web 产品化和公网交付。

最终项目完成了以下转变：

  • 从理解 Transformer 原理，发展到能够手写和数值验证。
  • 从本地模型脚本，发展到 OpenAI 兼容服务。
  • 从单次文档问答，发展到固定题集和量化评测。
  • 从合成训练数据，发展到 201 条可追溯真实数据。
  • 从只展示成功样例，发展到记录 17 轮实验和 8 项失败尝试。
  • 从本地 MVP，发展到可以公开访问的在线成品。
  • 从“希望微调有效”，发展到能够接受并解释原模型优于当前微调模型的真实结果。

这四周最重要的方法论是：所有结论都回到代码、日志和固定评测中验证；报告运行得到的结果，而不是预先希望得到的结果。

四、项目的AI辅助制作方案

1. 已采用的协作节奏

实际工作按“我下达每日任务 → AI阅读总纲与周计划 → 生成详细教程和脚本 → 我学习并运行修改 → 根据真实结果生成每日小汇报 → 每周形成阶段小结 → Git归档”推进。Git是保存文件版本和修改历史的工具。

每个学习日的教程、代码、笔记、截图和每日小汇报集中放入对应dayX目录；每周结束后再生成周工作报告、概念笔记汇总和算法题答案汇总。这种“每日记录 + 每周复盘”的统一格式，让四周中的每一项成果都能回到对应代码、日志和实验结果。

2. 任务拆分与验收

  1. 确定约束。 把6GB显存、机器人领域PDF、模型选择、目录位置和当天目标交给AI，要求先给可运行的最小步骤。
  2. 生成教程。 要求包含目标、名词解释、逐步命令、预期输出、常见报错和验收清单。带训练或测试的脚本在文件头说明模型、数据、损失函数、优化器以及测试内容。
  3. 本人执行。 阅读关键代码、运行命令，把实际日志交给AI分析。预期输出只是待验证目标，运行后再回填实测值。
  4. 定位问题。 检索错误先查召回片段，格式错误查提示词，风格问题查训练数据，接口错误查配置与服务身份，每轮只处理明确问题。
  5. 固定评测。 使用同一题集记录配置、结果与失败案例；自动判断后人工复核，保留修改口径。
  6. 整理交付。 AI依据实际日志编写README、日报与周报，本人核对数字和完成状态后归档。模型权重、向量库与适配器权重按项目规则排除在Git之外。

5. AI与本人的分工

AI辅助制定学习步骤、起草代码、解释报错和整理记录；本人负责目标选择、数据核对、实际运行、关键代码理解与最终验收。计算交给代码，事实判断回到资料，成果数字回到日志。

五、在线成品、实现边界与下一步

2. 在线版与本地评测的边界

在线Demo的检索层使用项目真实实现：bge Embedding、Chroma、Top-K与模板约束；由于免费CPU环境无法运行本地3B模型，在线生成层使用DeepSeek API。本地版使用Qwen2.5-3B-Instruct及LoRA adapter。

因此，本文全部评测数字来自本地Qwen链路，不代表在线Demo的DeepSeek生成效果。在线版用于展示交互与检索链路，本地版用于模型实验与量化对照。

3. 下一步

  • 将诊断实验中的关键词与向量检索互补真正接回生产链路，并测试Rerank重排序。
