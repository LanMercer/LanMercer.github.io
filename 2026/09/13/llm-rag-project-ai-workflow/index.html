大模型算法项目成果与AI辅助制作方案

作者： LanMercer
实践周期： 2026年8月起，MVP于9月3日完成归档
实践项目： 机器人行业垂直领域RAG问答系统
硬件环境： NVIDIA RTX 3060 Laptop，6GB显存
AI协作方式： 对话助手制定教程与解释原理，代码助手协助实现与排错，本人学习、运行、修改并验收

一、项目背景与目标

这次实践从大模型基础学习出发，逐步把本地部署、提示词工程、接口服务、文档检索和参数高效微调整合成一个可以演示、可以评测、有完整文档的项目。

RAG（检索增强生成）是先从资料里找到相关内容，再让模型依据这些内容回答。我的目标是围绕机器人领域PDF建立知识库，让回答能够追溯到资料，同时在资料没有答案时明确说明，而不是编造结论。

项目选用Qwen2.5-3B-Instruct作为生成模型。QLoRA是将量化后的模型底座与少量可训练参数结合的微调方法，使有限显存也能进行训练；LoRA adapter是保存这些增量参数的适配器。项目同时保留原模型和微调模型，便于观察两条链路的差异。

数学背景也贯穿了学习过程：用概率分布理解softmax，用加权平均理解注意力，用余弦相似度理解检索，用低秩近似理解LoRA。类比帮助入门，最终结论仍以公式、代码和实测结果为依据。

二、项目成果与核心产出

1. 从原理到工程的学习成果

  • Transformer原理验证： 手写多头注意力与官方实现对比，最大误差约为5e-07；序列倒序训练示例的测试结果为10/10。这些是教学实验结果，不代表通用任务能力。
  • 本地模型部署： Qwen2.5-3B-Instruct采用4bit量化加载，记录的模型显存占用约1.92GB，在6GB显存设备上跑通推理。该数值是当时的模型加载记录，不是训练峰值显存。
  • 提示词工程： 完成20个模板、5大分类，覆盖通用助手、文本处理、结构化抽取、推理问答和代码任务；通过实测迭代角色、输入、输出格式与约束。
  • 接口服务： 使用FastAPI（用于编写HTTP接口的Python框架）提供兼容的聊天接口，完成curl、Python requests和LangChain三种调用方式验证。LangChain用于组合模型调用与检索等处理步骤。
  • 文档问答： 跑通PDF加载、切块、向量化、建库、检索和生成完整流程；早期demo中3条论文问题回答正确，并记录了资料外问题的拒答样例。
  • 微调产物： 准备300条机器人行业SFT数据。SFT是用输入和期望回答进行监督训练；数据覆盖6类任务，记录为无重复。QLoRA训练参数为14,966,784，占约3.10B总参数的0.4827%，适配器约20～30MB。

2. 最终MVP实现了什么

MVP是能验证核心流程的最小可用版本。当前项目完成了领域文档建库、问答入口、原模型与微调模型切换、20题评测以及配套文档。

知识库使用GMR机器人论文，9页文档切成约105个片段。Embedding是把文本转换为可比较向量的模型，此处使用bge-small-zh-v1.5；Chroma是存放向量和文本的数据库，用于检索相关片段。

完整数据流： 用户问题 → 问题向量化 → 召回相关片段 → 拼接资料与提示词 → 模型生成 → 返回答案与引用。

项目分为四层：检索层负责找资料，答案组织层负责拼接上下文和约束，适配器负责调整回答风格，生成层负责输出回答。分层的意义是出错后可以逐层定位。

整合入口为第三周/day15/ask.py与config.json，支持--profile original和--profile lora。切换客户端配置时，还需启动对应模型服务；在6GB显存设备上，两种模型服务按需分别运行。

3. 配套交付文件

  • 建库脚本、原模型接口、微调模型接口与配置化问答入口。
  • 300条SFT数据、训练脚本和微调前后对比记录。
  • 20条评测题、eval.py评测脚本、逐题结果和人工复核记录。
  • 项目README、效果评估报告、双链路冒烟测试记录、架构图与面试四问。
  • 按日保存的教程和工作汇报，以及每周的工作、概念和算法题汇总。

三、真实评测结果与当前局限

1. 先明确评测口径

首版评测针对微调模型链路，配置为Top-K=4（每次取4个相关片段）、temperature=0.2，知识库为GMR论文。20题中，10题在资料内有答案，另外10题为资料外或反事实问题。

自动判分使用关键词与拒答词规则，之后逐题人工复核；Q9、Q18的误判已修正。以下数据来自Day14最终评测及Day15效果评估报告，并非本次撰文重新运行模型得到的结果。

2. 首版基线

  • 检索命中率：2/10，20%。 按标准答案段落是否被召回判定。
  • 资料内生成正确率：2/10，20%。 根据期望关键词并经人工复核判定。
  • 资料外防幻觉正确率：6/10，60%。 观察模型是否正确拒答。
  • 总正确率：8/20，40%。 对应这组两类各半的评测题。
  • 防幻觉F1：0.667。 F1是综合精确率与召回率的指标，此处精确率0.75、召回率0.60。

早期demo的“3问全对”与最终20题评测使用不同的问题集合，不能混为同一个准确率。首版低分最有价值的地方，是暴露了检索召回不足和生成错误。

3. 双链路观察

原模型与微调模型都完成了问答冒烟测试，也都有正确拒答样例。微调模型回答趋向简短、结论式；原模型往往更展开，引用格式更贴合模板。

例如，问论文实验使用哪个数据集时，一次冒烟测试中原模型答出LAFAN1，微调模型未点名；而此前评测中微调模型在同题答对。这个差异说明单次生成会波动，也说明风格变化不能直接当作事实准确率提升。

目前还没有完成原模型与微调模型在同一完整评测集上的量化对比，因此不写“微调提升了多少准确率”。

4. 需要继续解决的问题

检索层按首版标准有8/10题未命中答案段落，但精确段落匹配也可能漏记其他有效片段。后续需要同时观察标准段落命中与上下文是否包含答案证据。

20题的样本量较小，关键词规则不能完整判断事实正确性，单次生成也有随机性。当前结果用于建立项目基线，不直接推断真实用户场景的表现。

四、项目的AI辅助制作方案

1. 已采用的协作节奏

实际工作按“我下达每日任务 → AI阅读总纲与周计划 → 生成详细教程和脚本 → 我学习并运行修改 → 根据真实结果生成工作汇报 → Git归档”推进。Git是保存文件版本和修改历史的工具。

每个学习日的教程、代码、笔记、截图和报告集中放入对应dayX目录。每周学习五天，再用休息与复盘时间生成周工作报告、概念笔记汇总和算法题答案汇总。这种组织方式让每一项成果都能回到当时的代码和记录。

2. 任务拆分与验收

  1. 确定约束。 把6GB显存、机器人领域PDF、模型选择、目录位置和当天目标交给AI，要求先给可运行的最小步骤。
  2. 生成教程。 要求包含目标、名词解释、逐步命令、预期输出、常见报错和验收清单。带训练或测试的脚本在文件头说明模型、数据、损失函数、优化器以及测试内容。
  3. 本人执行。 阅读关键代码、运行命令，把实际日志交给AI分析。预期输出只是待验证目标，运行后再回填实测值。
  4. 定位问题。 检索错误先查召回片段，格式错误查提示词，风格问题查训练数据，接口错误查配置与服务身份，每轮只处理明确问题。
  5. 固定评测。 使用同一题集记录配置、结果与失败案例；自动判断后人工复核，保留修改口径。
  6. 整理交付。 AI依据实际日志编写README、日报与周报，本人核对数字和完成状态后归档。模型权重、向量库与适配器权重按项目规则排除在Git之外。

5. AI与本人的分工

AI辅助制定学习步骤、起草代码、解释报错和整理记录；本人负责目标选择、数据核对、实际运行、关键代码理解与最终验收。计算交给代码，事实判断回到资料，成果数字回到日志。

五、后续优化路线

以下是第四周计划中的待验证方案，目前没有新的评测结果可作为完成依据。

1. 优先改善检索

在固定题集下对比Top-K=4与8，再分别比较切块长度500与800。补充有效证据召回口径，检查英文论文与中文向量模型的适配问题，逐次保存实验结果。

2. 改善生成与引用

检查温度和模板约束，重点处理“有资料却拒答”“没有资料却拼凑回答”和引用格式偏离问题。关键问题进行多次生成，避免凭单次回答下结论。

3. 补齐微调对照

在相同题集、检索配置和提示词下，对原模型与微调模型分别评测事实正确性、拒答表现和风格。后续再考虑Rerank（对召回片段重新排序）与混合检索（结合关键词检索和向量检索）。

计划中的检索命中率≥40%、生成正确率≥40%等数值是优化目标，实际完成后再更新成果。

六、实践体会与资料依据

这次项目的收获，是把原理学习、代码实现、真实评测和文档归档连成一条可追溯的链路。AI帮助拆分任务与整理信息，实测与复核帮助我发现“能运行”之后还有哪些问题需要解决。

本文依据本地项目中的《我的总工作流程》《大模型算法学习成果汇报》、Day15项目README与效果评估报告、双链路测试记录，以及第四周项目总结与优化路线图整理。较早汇报中的进度描述有部分未同步，本文完成状态以Day15验收材料为准；第四周内容按后续计划呈现。
